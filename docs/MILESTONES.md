# 마일스톤

AgentDure는 프로젝트·버전 관리, LLM/에이전트 실행, Skills/MCP/외부 에이전트,
Slack/A2A 연동, 사용량 집계와 트레이스를 갖추고 있다. 이 문서는 구현 이력이 아니라
프로덕션 운영에 남은 작업만 우선순위대로 관리한다.

열린 마일스톤은 없다. 목록이 비어 있는 것은 할 일이 없다는 뜻이 아니라, *자동으로
확인 가능한 완료 조건을 갖춘* 작업이 지금은 하나도 등록돼 있지 않다는 뜻이다 (아래 규약
첫 항목). 완료된 것의 이력은 git log와 태그별 GitHub Release에 있다.

의도적으로 열지 않은 갭도 있다. 기록해 두는 이유는 "아직 안 했다"와 "안 하기로 했다"가
문서에서 구별되지 않으면 다음 사람이 같은 판단을 다시 하기 때문이다.

| 갭 | 왜 마일스톤이 아닌가 |
|---|---|
| Slack 이벤트의 급사 복구 | 재처리는 run이 비멱등이라는 이미 내린 판단에 걸리고, schedule의 "다음 발생"에 해당하는 자연스러운 재시도가 없다. 남는 것은 마감되지 않은 원장이 아니라 답을 못 받은 사용자 — 복구 대상이 아니라 이미 사용자에게 보이는 실패다 (ARCHITECTURE.md의 *Triggers*). |
| 인스턴스 간 즉시 무효화 | 강등된 admin·회전된 키가 다른 인스턴스에서 `SETTINGS_CACHE_TTL_MS`(기본 5초) 동안 유효하다. 공유 무효화 신호가 필요하고, TTL 기본값 자체가 그 트레이드오프를 재서 정한 값이다 (SECURITY.md의 *Operational notes*). |
| 기존 공개 이미지 URL의 소급 차단 | 이미 배포된 오브젝트는 이미 공개다. 행을 다시 써도 도달성은 바뀌지 않으므로, 버킷을 비공개로 만드는 운영 조치가 유일한 해결이고 그건 코드 작업이 아니다 (SECURITY.md의 *Data exposure and retention*). |

**결정이 필요한 갭은 또 다르다.** 위 표는 "안 하기로 했다"이고, 아래는 "완료 조건을 쓸 수
없어서 아직 마일스톤이 아니다"이다. 오른쪽 칸이 먼저 정해져야 하는 것이고, 그게 정해지는
순간 규약대로 위로 올라간다. 셋째 상태를 따로 두는 이유는 첫 표와 같다 — 판단이 *내려진*
갭과 판단이 *아직 없는* 갭이 한 칸에 섞이면 다음 사람이 어느 쪽인지 다시 알아내야 한다.

아래 네 건 중 뒤의 셋은 같은 문제를 1인용으로 푼 사내 Slack 에이전트
(`karrot-emu/yany-agent`)와 대조하다 드러났다. 그쪽 구현이 참고가 되지만 전제가 다르다는
것을 먼저 봐야 한다 — 사용자가 한 명이고, 프로젝트가 하나이며, 답을 스트리밍하지 않는다.
첫 건은 출처가 다르다: 하위 호환을 걷어냈다가 되돌린 결정이 남긴 질문이다. 같은 대조에서
나온 다섯째 갭 — 원격 에이전트 위임의 대화 연속성 — 은 닫혔다: 대화 키는
`RunOrigin.conversation` 이고, 키→`contextId` 매핑은 전송하는 프로젝트의 파티션에서
`RemoteConversationRepository` 가 소유한다 (ARCHITECTURE.md의 *A2A*).

| 갭 | 마일스톤이 되기 전에 정해야 하는 것 |
|---|---|
| MCP 하위 호환 계층의 수명 | 클라이언트는 `server/discover` 로 프로토콜 era 를 협상하고, OAuth 클라이언트도 메타데이터 문서 뒤에 RFC 7591 등록을 남겨 둔다. 둘 다 *의도적인* 하위 호환이다 — 레지스트리 항목이 가리키는 것은 남의 배포이고, 이쪽이 올라갔다는 이유로 남의 항목이 깨지면 그 소유자가 고칠 수 없다. 대가는 이 파일이 지고 있다: 레거시 연결만 갖는 세션 id, 만료 시 404 복구, teardown 의 DELETE, 그리고 그 해제가 취소된 런보다 오래 살게 하는 예외. 한 번 걷어냈다가 되돌린 코드다. 정할 것: **무엇을 관측해야 걷어낼 수 있는가** — 레지스트리의 모든 항목이 modern 이라는 사실을 어디서 읽는가(연결 시 협상 결과는 지금 아무 곳에도 기록되지 않는다), 그리고 등록으로만 클라이언트를 받은 프로젝트가 남아 있는지를 어떻게 세는가. 그 두 신호가 생기기 전에는 완료 조건을 쓸 수 없고, 생기는 순간 조건은 자명하다. |
| Slack 참여 판단의 다음 단계 | 위 두 갭(채널 무멘션 후속 / 답하지 않기로 하는 런)은 닫혔다 — 판단은 코드가 하고(`classifySlackEvent`), 참여 수명은 24시간이며, 판정이 claim·sink 보다 앞에 있어 침묵이 곧 "런이 아님"이다. 남은 것은 그 판단을 **모델이 하는 쪽**이다: 키워드는 운영자가 미리 적어야 하고, "이건 나한테 온 질문인가"를 문장 단위로 읽지는 못한다. 정할 것: 그 판정을 무엇이 수행하고 비용을 누가 지는가 — 채널 메시지마다 LLM 을 호출하면 프로젝트 일일 비용 가드가 런이 아닌 트래픽을 세게 되고, 오판이 채널에 그대로 남는다. 판정 결과를 관측할 자리(맞았는지 틀렸는지)가 없으면 완료 조건을 쓸 수 없다 — 아래 *답변 품질에 대한 사용자 신호* 와 같은 공백이다. |
| 답변 품질에 대한 사용자 신호 | 어떤 답이 좋았는지 말할 수 있는 자리가 어느 표면에도 없다. Slack 에는 네이티브 피드백 블록이 있지만 지금 답변은 blocks 가 아니라 markdown 으로 나가고, interactivity 엔드포인트도 없다(`/api/slack` 아래는 events 뿐). 정할 것: 신호를 어디에 적고 **무엇이 그것을 읽는지** — 읽는 쪽이 없으면 행만 쌓인다. |
| 런을 넘어 남는 것 (채널 메모리) | 버전의 프롬프트는 불변이라 사용자가 교정한 내용이 다음 런에 남는 축이 없다. 갈림길 둘 — 프로젝트에 붙는지 사람에 붙는지, 프롬프트에 주입되는지 도구로 조회되는지 — 은 Claude Tag 를 기준으로 삼으면 **답이 정해진다**: *장소*(채널)에 붙고, 주입되며, 쓰기는 대화로 한다("이 채널에서는 짧게 답해줘"). 막고 있던 결손은 사라졌다: 런은 이제 자기가 어느 대화에 있는지 안다 (`RunOrigin.conversation`, A2A `contextId` 와 같은 키), 그리고 모든 MCP 요청이 그 키를 `X-Conversation-Id` 로 나른다 — mcp-memory 가 스레드별 작업 메모를 프로젝트 공유 지식과 구분할 수 있는 채널이다. 남은 것은 **주입**이다: 지금 메모리는 도구로만 조회되고(모델이 `recall` 을 불러야 한다), 첫 토큰 전에 컨텍스트에 들어가는 길이 없다. 정할 것: 무엇이 무엇을 언제 주입하는가 — 버전 옵트인으로 첫 턴 전에 메모리 서버에 한 번 묻는지(비용은 런당 recall 한 번), 그 결과가 시스템 프롬프트의 어느 자리에 들어가야 프로바이더 캐시를 깨지 않는지, 그리고 저장되는 텍스트가 PII 필터의 어느 쪽인지. 콘솔에서 채널별로 적는 우회로가 있지만, 채널 id 를 손으로 붙여넣는 편집기는 이 기능의 쓸모를 거의 없앤다. |

기반 정리는 끝났다. 레이어 경계는 `tests/architecture.test.ts`가 강제한다 — 규칙 전부
허용 목록이 비어 있고, 이름 붙인 불변식은 저마다 소유 파일이 하나씩 지정돼 사본이
생기면 실패한다. 새 기능 작업은 그 위에 얹는다: 새 어댑터는 포트 뒤로 가고, 조립은
AGENTS.md가 명명한 wiring site에서만 하며(목록은 그쪽이 정본이다 — 여기 복제했던
사본은 한 번 낡았다), 새 실행 정책은 **run bracket** 한 곳
(`src/application/run/runBracket.ts`)에 붙는다.

실행 파사드가 아니다. `generateImage`를 직접 부르는 곳은 파사드 자신(`runProject.ts`)과
predict 라우트·A2A executor 셋이라, 그 두 라우트로 시작된 이미지 런은 파사드를 지나지
않는다 — 트리거처럼 `streamProjectRun`으로 들어오는 런은 지난다. 그래서 파사드에 붙인
정책은 이미지 런 전부에 적용되지 않는다. 반면 bracket은 top-level run을 admit하는 네 곳
모두에서 어떻게 시작됐든 그 런을 감싸는 단일 소유자이고, 일일 비용 가드·동시성 가드·미등록
모델 정책이 이미 거기 있다 (ARCHITECTURE.md의 *The run bracket*).

**규약**

- 각 마일스톤은 **완료 조건**을 자동으로 확인할 수 있어야 한다. 확인 방법이 정해지지
  않은 작업은 마일스톤에 넣지 않는다.
- "한 곳에만 있다"는 완료 조건은 **테스트로 고정한다** — `tests/architecture.test.ts`의
  single-owner 불변식이 그 자리다. 서술로만 남은 단일 소유는 다음 진입점이 생길 때
  조용히 깨진다.
- **선행**이 있는 마일스톤은 선행이 끝나기 전에 착수하지 않는다.
- **문서 순서가 우선순위이고, 기준은 *되돌릴 수 없는 정도* 다.** 심각도도 난이도도
  아니다 — 늦출수록 사후 복구가 불가능해지는 것이 위에 온다. 기록하지 않은 날의 감사
  기록은 소급 생성할 수 없고, 이미 나간 URL은 회수할 수 없다. 반대로 `running`으로 멈춘
  이력 행은 나중에도 마감할 수 있다. 순위를 바꾸려면 이 축에서 근거를 대야 한다.
- 완료된 마일스톤은 이 문서에서 제거한다. 이력은 git log와 태그별 GitHub Release
  (`.github/workflows/release.yml`가 커밋 목록으로 생성)가 source다.
- **마일스톤을 가리키는 문서가 그 마일스톤의 일부다.** 다른 문서가 같은 갭을 설명하는
  자리에 slug를 적어 두면 워크어라운드만 읽고 추적되지 않는 문제로 오해하는 것을 막을 수
  있다. 대가로, 범위를 좁히거나 마일스톤을 지울 때 참조도 함께 손봐야 한다 — 확인은
  `docs/`에서 slug를 grep 하는 것이고, 실제로 `trigger-durability`의 범위를 좁혔을 때 세
  곳이 옛 약속을 그대로 들고 있었다.
- 식별자는 **재사용하지 않는 slug**를 쓴다. 완료된 마일스톤을 지우는 규약 때문에 번호는
  반드시 재사용되고, 실제로 `M4`는 세 가지 서로 다른 기능을 가리킨 이력이 있다
  (API Reference 탭 → 프로젝트별 MCP 헤더 오버라이드 → 비용 임계값). 커밋 메시지의
  `(M4)`는 지금 어느 것도 가리키지 못한다.
- 동작 보존 작업은 기존 테스트를 수정해서 통과시키면 완료가 아니다.
