# 미완료 작업

현재 구현으로 해결되지 않은 작업과 아직 결정이 필요한 범위를 관리한다.
완료된 항목은 제거하며 이력은 git과 GitHub Release에 남긴다.
기존 제품의 동작·제약은 각 설계·운영 문서가 소유한다.

## 개편 공통 기준

[개편 목적](FEATURES.md#개편-목적)은 구조 단순화·명확화, 미사용 기능 제거, 핵심 Agent 실행에
대한 집중이다. 새 기능이나 범용 확장 플랫폼을 만드는 작업으로 범위를 넓히지 않는다.

- 부가 기능은 실사용 필요를 확인해 유지·통합·제거를 결정한다. 제거할 기능을 새 구조로 먼저 이식하지 않는다.
- 제거 대상은 UI뿐 아니라 전용 API·분기·설정·의존성·worker와 문서까지 정리한다. 비활성화만으로 완료하지 않는다.
- 필요한 권한·비용·승인·기록 보호와 핵심 사용 시나리오를 검증한다. 불필요한 메뉴·설정·실행 분기·운영 의존성이
  실제로 줄었는지도 변경 전후로 확인한다.
- 이미 합의한 개편 외의 신규 기능 추가는 범위에서 제외한다. 저장 데이터의 파괴적 처리는 별도로 승인받는다.

## agent-only-request-routing

[요청 기반 모델 역할 선택](FEATURES.md#확정된-개편-방향)의 미구현 범위다.
현재 Agent는 저장한 기본 모델·fallback과 별도 이미지 도구 모델을 사용한다.

완료 조건:

- 사용자 요청에 따라 다섯 모델 역할을 선택하고 실제 모델을 호출한다. 역할별 매핑·선택 정책·실패 처리는
  FEATURES의 미결정 세부사항을 확정한 뒤 구현한다.
- 선택한 역할·실제 모델·선택 사유 코드를 추적하고, 대표 요청으로 품질·비용·지연을 검증한다.
  후보 모델의 capability·사용 가능 여부·비용 정책을 검사하며 fallback과 재시도 범위를 제한한다.
- 요청별 모델 선택·이미지 처리·권한·사용량·실행 추적을 회귀 검증하고 관련 API·설계·기능 문서를 갱신한다.

## agent-entry-adapters

[기본 지원과 어댑터 경계](FEATURES.md#기본-지원과-어댑터-경계)를 구현한다. 현재 메시징에는
공통 턴 처리와 채널별 구현이 있지만, 실행 진입점·설정·알림 목적지까지 포함한 확장 계약으로
개편해야 한다. AG-UI도 아직 코드와 API 문서에 남아 있다.

완료 조건:

- 필수 인증·설정이 갖춰진 API·Chat·A2A가 선택적 어댑터 없이 같은 Agent를 실행한다.
- AG-UI endpoint·전용 실행/변환 코드·조립·예제·화면 노출과 문서를 제거하고,
  다른 경로가 사용하는 공통 스트리밍·도구 실행 기능은 유지한다.
- Slack·Telegram·Teams·Cron·Webhook을 공통 실행·출력 계약에 연결된 선택적 어댑터로 전환한다.
- 채널별 SDK·시크릿·이벤트 변환·응답 전달을 어댑터 경계에 두고, 권한·모델 선택·비용·실행 기록의
  공통 정책은 Agent 실행 코어에 남긴다. 등록·설정·활성화·배포 방식은 FEATURES의 미결정 항목을 확정한다.
- 예약 결과·비용 알림의 목적지와 전달 경로를 어댑터 계약으로 분리한다.
- Cron 어댑터 없이도 만료 데이터 정리 등 공통 운영 기능을 실행할 경로를 제공한다.
  현재 이 정리는 `src/app/api/triggers/scan/route.ts`의 예약 tick에 연결돼 있다.
- 테스트용 추가 어댑터를 구현·등록해 Agent 실행 코어의 채널별 분기 수정 없이 연결됨을 검증한다.
- 스트리밍·첨부·대화·취소·승인 같은 선택 기능은 어댑터별 지원 범위를 명시하고,
  미지원 기능을 조용히 생략하거나 기존 권한 경계를 약화하지 않는다.
- 어댑터 미설정·비활성·실패가 기본 경로의 부팅·실행을 막지 않는지, 각 어댑터의 인증·중복 처리·
  응답·사용량·Trace 계약이 유지되는지 회귀 검증하고 API·설계·기능 문서를 갱신한다.

두 개편 작업의 공통 검토 기준은 [변경 판단과 권고](FEATURES.md#변경-판단과-권고)를 따른다.
그 문서의 정리 후보는 사용 여부와 제거 범위를 확인할 대상이며, 새 기능 추가 목록이 아니다.

## release-event-gating

현재 [release.yml](../.github/workflows/release.yml)은 `pull_request`와 `v*` tag push를 받지만
`github-release`와 `release` job에는 tag 전용 조건이 없다. 따라서 PR에서도 Release 생성과
이미지 게시 작업을 시도한다. `gitops`에만 tag 조건이 있으며, ECR OIDC trust의 tag 제한은
GitHub Release job의 실행 조건을 대신하지 않는다.

완료 조건:

- PR에서는 게시 권한·registry 로그인·Release 생성 없이 검증 job만 실행한다.
- `v*` tag에서는 검증 성공 뒤 Release·앱/Sandbox 이미지 게시와 GitOps 전달이 실행된다.
- workflow의 이벤트·job 조건과 실제 PR/tag 실행 결과로 두 경로를 확인한다.
- [개발](DEVELOPMENT.md#ci)·[운영](OPERATIONS.md#릴리스-파이프라인)의 현재 제약 설명을 갱신한다.

## 결정이 필요한 범위

아래 기존 검토 항목도 이번 단순화의 필수 조건이 아니면 추가 구현하지 않는다.

| 주제 | 현재 상태 | 구현 전에 정할 것 |
|---|---|---|
| MCP 호환 경로의 수명 | transport의 era 협상과 dynamic client registration을 사용한다 | 협상 결과와 등록 방식의 관측 위치, 기존 원격 서버에 대한 지원 종료 기준. [MCP](design/mcp.md)를 따른다 |
| Slack의 의미 기반 참여 판단 | 코드의 참여 분류와 설정된 키워드를 사용한다 | 판정 모델·비용 귀속·오판 측정 기준. [Slack](design/slack.md#어떤-이벤트가-봇에게-온-것인가)을 따른다 |
| 답변 품질 피드백 | 사용자 평가를 수집·소비하는 제품 흐름이 없다 | 수집 표면·저장 형태·평가를 사용하는 주체·효과의 측정 기준 |

## 관리 기준

항목은 관찰 가능한 완료 조건과 검증 방법을 갖춰야 한다. 외부 서비스나 제품 판단이 필요한
내용은 위 결정 표에 남기고 이미 구현된 것처럼 설명하지 않는다.
식별자는 재사용하지 않는 slug를 사용하고, 항목을 완료하거나 범위를 바꾸면 참조 문서도 함께 고친다.
구조 변경의 완료는 해당 테스트로 확인하며, 기존 검사를 약화한 통과를 완료 근거로 삼지 않는다.
