# 마일스톤

AgentDure는 프로젝트·버전 관리, LLM/에이전트 실행, Skills/MCP/외부 에이전트,
Slack/A2A 연동, 사용량 집계와 트레이스를 갖추고 있다. 이 문서는 구현 이력이 아니라
프로덕션 운영에 남은 작업만 우선순위대로 관리한다.

## `bedrock-claude` — Bedrock 의 Claude 를 실행 가능하게

Bedrock 채널은 붙었지만 **Claude 는 이 경로로 못 간다.** Bedrock 의 OpenAI 호환
엔드포인트(`bedrock-mantle`)는 `anthropic.*` 모델에 대해
`does not support the '/v1/chat/completions' API` 로 400 을 낸다 — Claude 는 같은
엔드포인트의 **Anthropic Messages API**(`/v1/messages`)로만 열려 있다. 그래서 지금
레지스트리의 Bedrock offering 은 open-weight 모델뿐이고, 사내 AWS 계정으로 Claude 를
쓰려던 원래 동기는 아직 충족되지 않았다.

필요한 것은 두 번째 wire protocol 어댑터다: `LlmChannel` 포트의 두 번째 구현이
Messages 요청/스트리밍 이벤트/tool_use 블록/usage 를 도메인 청크로 옮긴다. 채널 선택은
이미 `ResolvedTarget` 이 들고 있는 정보로 충분하다 — 인증(`auth`)이 transport 를
갈랐듯 protocol 도 route 의 속성이다.

**완료 조건**: `bedrock/claude-*` offering 이 레지스트리에 있고, 그 id 로 시작한 런이
툴 호출을 포함해 끝까지 돌며 usage 행이 $0 이 아니다. 어댑터의 매핑은 `tests/` 에서
fake 로 고정한다 (`tests/fakeChannel.ts` 와 같은 자리).

**선행 없음.** 범위를 줄이려면 Claude 대신 Converse API 를 쓰는 선택지도 있으나, 그쪽은
OpenAI 호환도 Anthropic 호환도 아닌 세 번째 모양이라 얻는 것이 없다.

## `a2a-streaming-transfer` — 원격 에이전트 위임을 스트리밍으로

`sendA2aMessage` 는 `configuration.blocking: true` 로 한 번 쏘고 120초를 기다린다
(`src/infrastructure/a2a/client.ts`). 조사형 원격 에이전트는 답까지 분 단위가 걸리고 그
사이 커넥션에는 아무것도 흐르지 않는다. **게이트웨이는 그 침묵을 idle 로 보고 끊는다** —
이미 한 번 겪은 실패의 같은 모양이다(이미지 생성이 ALB 의 60초 idle timeout 에 걸린 건).
남는 것은 부분 답도 아니고 타임아웃 메시지다.

`A2AClient.sendMessageStream` 이 SDK 에 이미 있다. SSE 는 상태 업데이트가 흐르는 동안
커넥션을 살려 두므로 idle 판정 자체가 서지 않는다. 스트리밍은 카드의 capability 라
(`capabilities.streaming`), 지원하지 않는 카드에서는 generator 가 throw 한다 — 지금의
blocking 경로가 그대로 폴백이고, 새 설정 항목이 필요하지 않다.

**완료 조건**: fake fetch 가 SSE 로 답하는 원격 에이전트에서 마지막 이벤트까지의 텍스트와
이미지가 지금과 같은 `A2aSendResult` 로 모이고, blocking 타임아웃보다 긴 무전송 구간이
있어도 끊기지 않는다. `capabilities.streaming` 이 없는 카드는 blocking 으로 떨어져 결과가
동일하다. 두 경로 모두 `tests/a2a.test.ts` 에 고정한다.

**선행 없음.**

## `slack-channel-progress` — 채널 스레드에도 진행이 보이게

Slack 답변 sink 는 첫 *텍스트* 델타에서 열린다(`src/application/slack/replyStream.ts` 의
`push`). 네이티브 상태 줄은 DM 에만 있으므로(`assistantThread`), **채널 스레드에서 툴만
오래 도는 런은 첫 토큰이 나올 때까지 아무 흔적도 남기지 않는다.** 사용자가 보는 것은 자기
멘션뿐이고, 그것은 답이 오는 중인 런과 죽은 봇을 구별하지 못한다. DM 에서는 상태 줄과
하트비트가 이미 그 구별을 해 준다 — 갭은 채널에만 있다.

sink 는 그 모양을 이미 절반 갖고 있다: edit 모드는 메시지를 먼저 올리고 제자리에서
갱신한다. 없는 것은 *텍스트 없이 여는 이유* 이고, 첫 툴 청크가 그 이유가 된다.

**완료 조건**: 텍스트 델타 없이 툴 청크만 오는 채널 스레드 런이 스레드에 메시지를 하나
게시하고, 최종 답이 같은 `ts` 를 갱신한다(새 메시지가 아니다). DM 은 지금 그대로 상태 줄만
쓰고 메시지 수를 늘리지 않는다. `tests/slackReplyStream.test.ts` 와
`tests/handleSlackEvent.test.ts` 에 고정한다.

**선행 없음.**

---

새로 추가된 두 건이 `bedrock-claude` 아래인 이유: 되돌릴 수 없는 정도 축에서 둘 다 *이미
사용자에게 보이는 실패* 라 사후 복구의 대상이 아니다(아래 표의 Slack 급사 복구와 같은
논리). 그 축은 셋을 서로 구별하지 못하므로 기존 순서를 유지하고 아래에 붙였다.

다른 열려 있는 마일스톤은 없다. 목록이 짧은 것은 할 일이 없다는 뜻이 아니라,
*자동으로 확인 가능한 완료 조건을 갖춘* 작업이 지금은 이 셋뿐이라는 뜻이다 (아래 규약 첫 항목).
직전까지 있던 네 건 — webhook 딜리버리 급사 복구, 생성 이미지의 공개 URL 제거, 감사
기록의 일급 엔티티 승격, 미등록 모델 실행 거부 옵션 — 은 구현되어 규약대로 제거됐다.
이력은 git log와 태그별 GitHub Release에 있다.

의도적으로 열지 않은 갭도 있다. 기록해 두는 이유는 "아직 안 했다"와 "안 하기로 했다"가
문서에서 구별되지 않으면 다음 사람이 같은 판단을 다시 하기 때문이다.

| 갭 | 왜 마일스톤이 아닌가 |
|---|---|
| Slack 이벤트의 급사 복구 | 재처리는 run이 비멱등이라는 이미 내린 판단에 걸리고, schedule의 "다음 발생"에 해당하는 자연스러운 재시도가 없다. 남는 것은 마감되지 않은 원장이 아니라 답을 못 받은 사용자 — 복구 대상이 아니라 이미 사용자에게 보이는 실패다 (ARCHITECTURE.md의 *Triggers*). |
| 인스턴스 간 즉시 무효화 | 강등된 admin·회전된 키가 다른 인스턴스에서 `SETTINGS_CACHE_TTL_MS`(기본 5초) 동안 유효하다. 공유 무효화 신호가 필요하고, TTL 기본값 자체가 그 트레이드오프를 재서 정한 값이다 (SECURITY.md의 *Operational notes*). |
| 기존 공개 이미지 URL의 소급 차단 | 이미 배포된 오브젝트는 이미 공개다. 행을 다시 써도 도달성은 바뀌지 않으므로, 버킷을 비공개로 만드는 운영 조치가 유일한 해결이고 그건 코드 작업이 아니다 (SECURITY.md의 *Data exposure and retention*). |

**결정이 필요한 갭은 또 다르다.** 위 표는 "안 하기로 했다"이고, 아래는 "완료 조건을 쓸 수
없어서 아직 마일스톤이 아니다"이다. 오른쪽 칸이 먼저 정해져야 하는 것이고, 그게 정해지는
순간 규약대로 위로 올라간다. 셋째 상태를 따로 두는 이유는 첫 표와 같다 — 판단이 *내려진*
갭과 판단이 *아직 없는* 갭이 한 칸에 섞이면 다음 사람이 어느 쪽인지 다시 알아내야 한다.

다섯 건 모두 같은 문제를 1인용으로 푼 사내 Slack 에이전트(`karrot-emu/yany-agent`)와
대조하다 드러났다. 그쪽 구현이 참고가 되지만 전제가 다르다는 것을 먼저 봐야 한다 —
사용자가 한 명이고, 프로젝트가 하나이며, 답을 스트리밍하지 않는다.

| 갭 | 마일스톤이 되기 전에 정해야 하는 것 |
|---|---|
| 원격 에이전트 위임의 대화 연속성 | A2A 는 `message.contextId` 로 같은 대화를 잇는데 `sendA2aMessage` 는 매 호출을 새 대화로 보낸다. 같은 스레드에서 두 번 물으면 원격 쪽은 두 번 다 콜드 스타트다. 서버 방향(`application/a2a/executor.ts`)은 contextId 를 다루므로 이건 클라이언트 방향만의 비대칭인데, 막는 것은 어댑터가 아니라 **대화 키가 실행 계층에 없다**는 사실이다 — `RunOrigin` 이 나르는 것은 actor·caller·ancestry 뿐이고 Slack 의 thread_ts 도 채팅의 id 도 거기까지 내려오지 않는다. 정할 것: 무엇을 대화 키로 삼고, 키→contextId 매핑을 누가 소유하는가. |
| 채널 스레드에서 멘션 없는 후속 | 지금은 채널의 매 턴이 @멘션을 요구한다(`bot_events` 에 `message.channels` 가 없다 — `projectSlack.ts` 의 매니페스트). 참여 표시를 저장하면 후속을 받을 수 있지만, 그 순간 봇은 채널 히스토리 전량을 받고 "이 메시지가 나에게 온 것인가"를 런마다 판단해야 한다. 정할 것: 참여의 수명, 그리고 그 판단을 코드가 하는지 모델이 하는지 — 후자면 아래 항목이 선행이 아니라 **같은 결정의 나머지 절반**이다. |
| 답하지 않기로 하는 런 | 위가 도입되면 필요해진다. 어려운 쪽은 규약이 아니라 스트리밍이다 — sink 는 첫 델타에서 열리므로, 모델이 침묵을 *출력해서* 알리는 방식은 이미 열린 메시지를 지우는 일이 된다(그 방식이 성립하는 참고 구현은 최종 답만 쓰는 non-streaming 이다). 정할 것: 판정을 첫 델타 앞에 두는 방법 — sink 열기를 유예할지, 판정을 런 밖으로 뺄지. |
| 답변 품질에 대한 사용자 신호 | 어떤 답이 좋았는지 말할 수 있는 자리가 어느 표면에도 없다. Slack 에는 네이티브 피드백 블록이 있지만 지금 답변은 blocks 가 아니라 markdown 으로 나가고, interactivity 엔드포인트도 없다(`/api/slack` 아래는 events 뿐). 정할 것: 신호를 어디에 적고 **무엇이 그것을 읽는지** — 읽는 쪽이 없으면 행만 쌓인다. |
| 런을 넘어 남는 것 | 버전의 프롬프트는 불변이라 사용자가 교정한 내용이 다음 런에 남는 축이 없다. 갈림길이 둘이다: 프로젝트에 붙는지 사람에 붙는지, 그리고 프롬프트에 주입되는지 도구로 조회되는지. 후자라면 `mcp-memory` 가 이미 그 자리일 수 있다. 정할 것: 그 두 갈래 — 확인 전에는 범위도 완료 조건도 쓸 수 없다. |

기반 정리는 끝났다. 레이어 경계는 `tests/architecture.test.ts`가 강제한다 — 규칙 전부
허용 목록이 비어 있고, 이름 붙인 불변식은 저마다 소유 파일이 하나씩 지정돼 사본이
생기면 실패한다. 새 기능 작업은 그 위에 얹는다: 새 어댑터는 포트 뒤로 가고, 조립은
AGENTS.md가 명명한 wiring site에서만 하며(목록은 그쪽이 정본이다 — 여기 복제했던
사본은 한 번 낡았다), 새 실행 정책은 **run bracket** 한 곳
(`src/application/run/runBracket.ts`)에 붙는다.

실행 파사드가 아니다. `generateImage`를 직접 부르는 곳은 파사드 자신(`runProject.ts`)과
predict 라우트·A2A executor 셋이라, 그 두 라우트로 시작된 이미지 런은 파사드를 지나지
않는다 — 트리거처럼 `streamProjectRun`으로 들어오는 런은 지난다. 그래서 파사드에 붙인
정책은 이미지 런 전부에 적용되지 않는다. 반면 bracket은 top-level run을 admit하는 네 곳
모두에서 어떻게 시작됐든 그 런을 감싸는 단일 소유자이고, 일일 비용 가드·동시성 가드·미등록
모델 정책이 이미 거기 있다 (ARCHITECTURE.md의 *The run bracket*).

**규약**

- 각 마일스톤은 **완료 조건**을 자동으로 확인할 수 있어야 한다. 확인 방법이 정해지지
  않은 작업은 마일스톤에 넣지 않는다.
- "한 곳에만 있다"는 완료 조건은 **테스트로 고정한다** — `tests/architecture.test.ts`의
  single-owner 불변식이 그 자리다. 서술로만 남은 단일 소유는 다음 진입점이 생길 때
  조용히 깨진다.
- **선행**이 있는 마일스톤은 선행이 끝나기 전에 착수하지 않는다.
- **문서 순서가 우선순위이고, 기준은 *되돌릴 수 없는 정도* 다.** 심각도도 난이도도
  아니다 — 늦출수록 사후 복구가 불가능해지는 것이 위에 온다. 기록하지 않은 날의 감사
  기록은 소급 생성할 수 없고, 이미 나간 URL은 회수할 수 없다. 반대로 `running`으로 멈춘
  이력 행은 나중에도 마감할 수 있다. 순위를 바꾸려면 이 축에서 근거를 대야 한다.
- 완료된 마일스톤은 이 문서에서 제거한다. 이력은 git log와 태그별 GitHub Release
  (`.github/workflows/release.yml`가 커밋 목록으로 생성)가 source다.
- **마일스톤을 가리키는 문서가 그 마일스톤의 일부다.** 다른 문서가 같은 갭을 설명하는
  자리에 slug를 적어 두면 워크어라운드만 읽고 추적되지 않는 문제로 오해하는 것을 막을 수
  있다. 대가로, 범위를 좁히거나 마일스톤을 지울 때 참조도 함께 손봐야 한다 — 확인은
  `docs/`에서 slug를 grep 하는 것이고, 실제로 `trigger-durability`의 범위를 좁혔을 때 세
  곳이 옛 약속을 그대로 들고 있었다.
- 식별자는 **재사용하지 않는 slug**를 쓴다. 완료된 마일스톤을 지우는 규약 때문에 번호는
  반드시 재사용되고, 실제로 `M4`는 세 가지 서로 다른 기능을 가리킨 이력이 있다
  (API Reference 탭 → 프로젝트별 MCP 헤더 오버라이드 → 비용 임계값). 커밋 메시지의
  `(M4)`는 지금 어느 것도 가리키지 못한다.
- 동작 보존 작업은 기존 테스트를 수정해서 통과시키면 완료가 아니다.
