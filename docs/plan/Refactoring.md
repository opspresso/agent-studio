# Architecture-driven Refactoring

현재 프로젝트는 바이브코딩으로 빠르게 기능을 추가하면서 코드와 문서가 점점 복잡해지고 있습니다.

기능을 새로 구현하기 전에, 현재 프로젝트 전체를 분석하고 **아키텍처, 재사용성, 유지보수성, 일관성 관점에서 점진적으로 리팩토링**해 주세요.

## 목표

기존 동작을 최대한 유지하면서 다음을 개선합니다.

* 명확한 아키텍처와 책임 분리
* 코드 중복 제거
* 공통 로직 재사용
* 모듈 간 결합도 감소
* 적절한 추상화
* 불필요한 추상화 제거
* 파일 및 디렉터리 구조 단순화
* 일관된 네이밍과 패턴 적용
* 사용되지 않는 코드 제거
* 문서 중복 및 오래된 내용 제거
* 코드와 문서 간 불일치 해결
* 새로운 기능을 쉽게 추가할 수 있는 구조 유지

## 1. 현재 구조 분석

먼저 코드를 수정하지 말고 프로젝트를 분석하세요.

다음을 파악합니다.

* 전체 디렉터리 구조
* 주요 모듈과 책임
* 데이터 흐름
* 의존성 관계
* 공통으로 사용되는 코드
* 중복 구현
* 지나치게 큰 파일 / 클래스 / 함수
* 서로 다른 계층의 책임이 섞여 있는 부분
* 강하게 결합된 모듈
* 순환 의존성
* 불필요한 wrapper / abstraction
* dead code
* 임시 구현 및 workaround
* 유사하지만 서로 다르게 구현된 패턴
* 코드와 문서가 불일치하는 부분

특히 동일하거나 유사한 역할을 하는 코드가 여러 곳에 존재하는지 확인하세요.

## 2. Architecture 정의

현재 프로젝트의 규모와 특성에 맞는 가장 단순한 아키텍처를 사용하세요.

무조건 새로운 레이어나 디자인 패턴을 추가하지 마세요.

다음 원칙을 우선합니다.

* High Cohesion
* Low Coupling
* Single Responsibility
* Separation of Concerns
* DRY
* KISS
* 명확한 dependency direction
* Composition over inheritance
* 필요한 만큼만 추상화

현재 코드베이스에서 이미 잘 사용되고 있는 패턴이 있다면 새로운 패턴을 도입하기보다 기존 패턴을 표준으로 삼으세요.

## 3. 재사용성 검토

비슷한 코드가 여러 곳에서 사용된다면 공통화 가능성을 검토하세요.

단, 단순히 코드 몇 줄이 같다는 이유만으로 추상화하지 마세요.

다음 조건을 만족할 때 공통화를 고려합니다.

* 동일한 책임을 가진다.
* 변경 이유가 같다.
* 앞으로도 함께 변경될 가능성이 높다.
* 명확한 API 또는 interface로 표현할 수 있다.

반대로 서로 다른 도메인 책임을 가진 코드는 우연히 코드가 비슷하더라도 분리해서 유지하세요.

## 4. Refactoring 기준

다음 우선순위로 개선합니다.

1. 잘못된 책임 분리
2. 중복된 비즈니스 로직
3. 강한 모듈 결합
4. 복잡한 dependency
5. 지나치게 큰 파일 / 함수 / 클래스
6. 반복되는 utility / helper
7. inconsistent naming
8. dead code
9. 불필요한 abstraction
10. 디렉터리 구조

리팩토링 과정에서 단순히 파일을 잘게 쪼개는 것을 좋은 구조라고 판단하지 마세요.

파일 개수가 늘어나는 것보다 **코드를 찾고 이해하기 쉬운 구조**를 우선합니다.

## 5. 문서 정리

코드뿐 아니라 프로젝트 문서도 함께 정리하세요.

다음을 확인합니다.

* 중복 문서
* 오래된 설계 문서
* 현재 코드와 다른 설명
* 여러 문서에 흩어진 동일한 내용
* 필요 이상으로 상세한 구현 설명
* AI가 생성했지만 실질적인 가치가 없는 문서

문서는 가능한 한 다음 구조로 정리합니다.

* README
* Architecture
* Development Guide
* API / Interface
* 주요 설계 결정(필요한 경우 ADR)

코드를 보면 알 수 있는 내용을 문서에서 반복하지 마세요.

문서는 **왜 이렇게 설계했는지**, **어떤 제약이 있는지**, **어떻게 확장해야 하는지**를 중심으로 유지하세요.

## 6. 작업 방식

Big Bang Refactoring을 하지 마세요.

작은 단위로 진행합니다.

각 단계마다:

1. 문제를 설명합니다.
2. 왜 변경해야 하는지 설명합니다.
3. 변경 범위를 정의합니다.
4. 코드를 수정합니다.
5. 테스트 / 타입체크 / 린트를 실행합니다.
6. 기존 동작이 유지되는지 확인합니다.
7. 관련 문서를 업데이트합니다.

가능하면 하나의 리팩토링 단계가 독립적인 commit이 될 수 있을 정도의 크기로 유지하세요.

## 7. 변경 전 계획

실제 수정 전에 다음 형태로 리팩토링 계획을 먼저 작성하세요.

### Findings

현재 발견된 주요 구조적 문제

### Target Architecture

현재 프로젝트에 적합한 목표 구조

### Refactoring Candidates

각 항목마다:

* 문제
* 위치
* 영향 범위
* 제안
* 기대 효과
* 위험도
* 우선순위

### Execution Plan

P0 / P1 / P2 수준으로 작업 순서를 제안하세요.

* P0: 구조적 문제 또는 유지보수 리스크가 큰 부분
* P1: 중복 제거 / 재사용성 / 모듈화
* P2: 네이밍 / 문서 / 디렉터리 / cleanup

계획을 작성한 뒤 가장 안전하고 효과가 큰 항목부터 실제 리팩토링을 진행하세요.

## 8. 중요한 제약

* 기존 기능을 임의로 제거하지 마세요.
* API와 외부 인터페이스는 특별한 이유가 없다면 유지하세요.
* 테스트를 깨뜨리지 마세요.
* 새로운 dependency 추가를 최소화하세요.
* 과도한 디자인 패턴을 도입하지 마세요.
* 미래에 필요할 것이라는 이유만으로 abstraction을 만들지 마세요.
* 단순히 코드 줄 수를 줄이는 것을 목표로 하지 마세요.
* 리팩토링 자체가 목적이 아니라 프로젝트의 이해도와 변경 용이성을 높이는 것을 목표로 하세요.

최종적으로 개발자가 다음 질문에 쉽게 답할 수 있는 구조를 만들어 주세요.

* 이 기능은 어디에 구현되어 있는가?
* 이 로직의 책임은 어디에 있는가?
* 비슷한 코드를 새로 작성하지 않고 재사용할 수 있는가?
* 변경하면 어떤 부분에 영향을 주는가?
* 새로운 기능은 어느 레이어 / 모듈에 추가해야 하는가?

**Prefer simplification over abstraction.
Prefer consistency over cleverness.
Prefer incremental refactoring over rewriting.**
